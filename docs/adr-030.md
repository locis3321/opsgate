# ADR-030：MCP `?group=` 改为按分组实体过滤（并新增 `?category=`）

- **状态**：已确认（2026-11-13，用户实测反馈后拍板）
- **取代**：ADR-026 §3「实现态事实校正」中「`?group=` 按 `category` 过滤」的现状（该段只登记了事实，未决议改法）
- **保留**：ADR-026 的核心结论不变——**分组是自由组织单元，不构成对资产的业务限定**（能否调用仍只由 `can()` 决定）

---

## 1. 背景

用户在 opencode 中通过 API Key 连接 `/mcp`（URL 未带 `?group=`），实测：

- `opsgate_list_assets` 返回 `[]`
- `opsgate_list_groups` 显示 3 个分组，但成员均为 0

排查结论（两条叠加）：

1. `GROUP_DEFAULT = 'host'`（`src/services/mcpEndpoint.ts`）——不带参数时默认只给 `category=host` 的资产；该部署资产只有 `k8s` 与 `mysql`，因此**必然为空**。
2. `?group=<x>` 的实现是 `WHERE category = <x>`（`src/services/toolAggregation.ts`）——**分组实体（`groups` / `group_servers` / `group_users`）完全没有参与过滤**。

即：UI 上建的"分组"在 MCP 侧根本不起作用，而参数名 `group` 又让人以为是分组实体。这是**名实不符**，会让用户按错误心智模型配置权限。

## 2. 决策

### 2.1 `?group=` 改为按分组实体过滤

`?group=<分组名或分组 id>` → 返回**该分组内、且当前 principal 有 `can('view')` 的资产**。

理由：参数名就叫 group；用户在 UI 里维护的是分组；两边语义必须一致，否则"分组"两字在系统里有两个含义。

### 2.2 新增 `?category=` 承担原有的品类收窄

原「按品类收窄」是有用的能力（如"只给我 mysql 工具"），不能丢，因此独立成 `?category=`。

### 2.3 默认值改为 `all`

不带 `?group=` 且不带 `?category=` → 全部可见资产。

**默认值必须是「我能看到的全部」**。默认收窄到某个集合是危险的：用户不知道有收窄，看到空列表会以为没资产（本次事故即为实例）。收窄必须由调用方显式声明。

### 2.4 两者的关系

| 参数 | 语义 | 缺省 |
|---|---|---|
| `?group=` | 分组实体（`group_servers` 关联） | 不限分组 |
| `?category=` | 资产品类（`host/mysql/k8s/other`） | 不限品类 |

同时给出时取**交集**；分组不存在 → 400（不静默返回空，避免与"分组内无资产"混淆）。

### 2.5 与 `can()` 的关系（不变）

- **分组不是授权**：`?group=` 只是**视图筛选**，最终每条资产仍过 `can('view', principal, asset)`（R-3 单真值源不变）。
- 因此 `?group=` 只能**收窄**，不可能放大可见范围。
- `groups` 的用户成员关系（`group_users`）**不参与** MCP 可见性判定——可见性是资自身的事实（owner/visibility/sharedWithUserIds），分组只是组织的视图。

## 3. 影响

| 部位 | 变化 |
|---|---|
| `src/services/toolAggregation.ts` | `AggregateInput` 增加 `category`；分组过滤改为 join `group_servers` |
| `src/services/mcpEndpoint.ts` | `GROUP_DEFAULT='all'`；解析 `?category=`；分组不存在时 400 |
| `src/routes/mcp.ts` | `/mcp`、`/mcp/preview`、`DELETE /mcp` 透传 `category` |
| `buildInstructions` | 说明文字区分"分组视图"与"品类收窄" |
| Spec §5.5 / §5.5.6 | 契约描述更新（`?group=` 语义、新增 `?category=`） |
| 测试 | 新增分组过滤、交集、分组不存在 400、默认 all 的用例 |

**破坏性变更**：原来用 `?group=k8s` 想当然按品类过滤的调用方，改造后会得到 400（不存在名为 k8s 的分组）或空集。需在 Spec 中标注为 v1 契约修正，并说明迁移方式（改用 `?category=k8s`）。

## 4. 不做

- 不让 `group_users` 参与可见性（那会变成"分组即授权"，与 ADR-026 冲突）。
- 不做多分组 OR 查询（`?group=a&group=b`）——本次无需求，需要时另议。
- 不改 `can()` 的任何判定逻辑。
